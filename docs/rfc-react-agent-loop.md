# RFC: ReAct Agent Loop

Status: Proposed  
Date: 2026-06-09  
Owner: LexCatalyst product/backend

---

## 1. Problem Statement

The current chat pipeline is single-shot RAG:

```
embed query → pre-fetch docs + KB + memories → stuff into system prompt → call LLM once
```

The LLM has no agency over what it searches, how many sources it retrieves, or whether the retrieved context is actually sufficient to answer the question. For complex legal questions this produces shallow answers: either too much irrelevant context (noise) or missing context the LLM would have found if it could have asked for more.

---

## 2. Proposed Architecture

Replace the single-shot pipeline with a **ReAct (Reasoning + Acting) loop**:

```
user message
    │
    ▼
system prompt + memories + history
    │
    ▼
┌─────────────────────────────────┐
│  LLM call with tools available  │◄──────────────────┐
└─────────────────────────────────┘                   │
    │                                                  │
    ├── tool_calls in response ──► execute tools ──────┘
    │                              (max 5 rounds)
    └── final answer ──► stream tokens to user
```

The LLM decides what to search, inspects results, and decides whether it needs more before committing to a final answer.

---

## 3. Tools

Four tools exposed to the agent:

| Tool | Description | Backed by |

| `search_documents` | Semantic search over uploaded document chunks | `rag_service.search_documents` |

## 4. What is Pre-loaded vs Tool-fetched

**Pre-loaded** (always in system prompt, not exposed as tools):
- User memories — small, always relevant, no need for a round-trip

**Tool-fetched** (agent decides when and what to search):
- Document chunks — agent searches only when the question needs document evidence
- KB entries — agent searches only when the question needs firm/team knowledge
- Full KB entry content — agent fetches only if a search result warrants deeper reading

This eliminates the current problem of stuffing all retrieved context into the prompt regardless of relevance.

---

## 5. Streaming Protocol

Two new SSE event types alongside the existing `thread / token / done / error`:

```
event: tool_call
data: {"tool": "search_knowledge_bank", "args": {"query": "APAC governing law precedents"}}

event: tool_result
data: {"tool": "search_knowledge_bank", "summary": "Found 2 entries: Governing law precedents · Partner pref — Sunita Rao"}
```

The `tool_result` summary is a short human-readable description of what was found, generated by the tool execution layer rather than the LLM.

---

## 6. User-Facing Display

Tool steps render inline above the final answer, collapsed by default on desktop and expandable:

```
🔍 Searching documents for "survival period M&A NDA"…
📚 3 chunks found — Meridian NDA v2.pdf
🧠 Searching knowledge bank for "NDA survival clause precedent"…
✅ 2 KB entries found — M&A NDA playbook · clause 7.2, Oaktree SPA precedent

The standard market position for M&A NDAs is 5 years minimum…
```

---

## 7. Data Model Changes

No schema changes required. The agent loop is purely a service-layer change. The final assistant message is saved to `chat_messages` as before — tool steps are not persisted (they are ephemeral streaming events).

## 8. Implementation Plan

### 8.1 Backend

**`app/providers/deepseek.py`**
- Add `stream_with_tools(messages, tools, model)` async generator
- Handles streaming + accumulating `delta.tool_calls` chunks
- Yields `("token", content)`, `("tool_calls", [tool_call, ...])`, or `("done", usage)`

**`app/services/agent_service.py`** (new)
- `TOOLS` — list of tool definitions
- `execute_tool(name, args, db, user_id, matter_id)` — dispatches to the correct service function, returns a structured result
- `make_tool_result_summary(name, result)` — generates the short human-readable summary for `tool_result` events
- `run_agent_loop(messages, db, user_id, matter_id, model, *, on_tool_call, on_tool_result, on_token)` — async generator that drives the ReAct loop, max 5 rounds

**`app/services/chat_service.py`**
- Replace `create_chat_request` pre-fetch with call to `run_agent_loop`
- Memories still pre-loaded into system prompt before the loop starts

**`app/main.py`**
- Streaming endpoint yields `tool_call` and `tool_result` SSE events between `thread` and `token` events

### 8.2 Frontend

**`frontend/src/types/workspace.ts`**
```typescript
type ToolStep = {
  tool: string
  args: Record<string, string>
  summary: string | null   // null while running
  status: 'running' | 'done'
}

// Message gains:
steps?: ToolStep[]
```

**`frontend/src/lib/api.ts`**
- Add `tool_call` and `tool_result` to `StreamChatOptions` callbacks
- Wire up `handleStreamEvent` for the two new event types

**`frontend/src/App.tsx`**
- Track `steps` on the active assistant draft message
- `onToolCall`: add a `running` step
- `onToolResult`: update matching step to `done` with summary

**`frontend/src/components/ChatPanel.tsx`**
- Render `steps` above the message body when present
- Each step: icon (🔍 for search, 📚 for doc result, 🧠 for KB/memory) + label + status indicator

## 9. Loop Safety

- **Max iterations**: 5 tool-call rounds. After round 5, the loop sends a `tool_calls_exhausted` system message and the LLM must answer with what it has.
- **Empty tool results**: handled gracefully — tool returns `"No results found"` as its content so the LLM can decide to try a different query or answer from memory.
- **Abort**: if the client aborts mid-loop (user stops generation), the async generator exits cleanly. Partially-completed tool steps are discarded.

## 10. Build Order

1. `deepseek.py` — `stream_with_tools` generator
2. `agent_service.py` — tool definitions + execution + loop
3. `chat_service.py` — wire loop into streaming path
4. `main.py` — emit new SSE events
5. `types/workspace.ts` — `ToolStep` type
6. `api.ts` — new stream event handlers
7. `App.tsx` — step state management
8. `ChatPanel.tsx` — step rendering

---

## 11. Out of Scope

- Persisting tool steps to the database
- Parallel tool calls (the loop is sequential for now; parallelism adds complexity without clear benefit for legal Q&A)
- Agent memory of past tool results across turns (each turn starts fresh)
- Custom tool definitions per user or firm
